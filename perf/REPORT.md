# 채널 홈 피드 성능 개선 보고서

## 요약

채널 홈(게시글 피드)의 모바일 LCP를 5,240 ms에서 2,434 ms로 줄였다(−54%). 조건은 Lighthouse devtools 스로틀링, 5회 중앙값, 범위가 겹치지 않음이다.

| 지표 (devtools, 모바일, 5회) | 변경 전 `f693c2e`      | 변경 후 `cff48c8`      | 판정      |
| ---------------------------- | ---------------------- | ---------------------- | --------- |
| LCP                          | 5,240 ms (5,215–5,660) | 2,434 ms (2,428–2,436) | −54%      |
| Speed Index                  | 5,532 ms (5,510–5,775) | 3,025 ms (3,017–3,060) | −45%      |
| CLS                          | 0                      | 0                      | 유지      |
| FCP                          | 2,058 ms (2,040–2,065) | 2,102 ms (2,010–2,128) | 차이 없음 |
| TBT                          | 325 ms (319–413)       | 385 ms (371–392)       | 차이 없음 |
| Lighthouse 점수              | 67 (64–67)             | 86 (86–87)             | +19       |
| JS 전송                      | 267.4 KiB              | 274.2 KiB              | +6.8 KiB  |

변경은 커밋 3개다. 단계별 수치는 [LOG.md](LOG.md)에 있다.

1. `9a899a5` 첫 페이지 게시글 SSR: 단독으로는 LCP 차이 없음
2. `adabb4a` SSR로 받은 게시글의 등장 애니메이션 생략: LCP 개선, CLS 0.078 발생
3. `cff48c8` 날짜 바 높이 고정: CLS 0으로 복구

## 진단

### 원인: 이미지 요청이 JS 실행과 API 응답 뒤에 있었다

변경 전 채널 홈의 요청 순서는 다음과 같았다.

1. HTML
2. JS 번들
3. `/api/me`, `/api/posts` (클라이언트 SWR)
4. 게시글 이미지(`_next/image`)

- 게시글 이미지(LCP 요소)의 요청 시작은 5,052 ms(중앙값)였다.
- 페이지에는 `오늘 날짜에 해당하는 게시글 SSR 처리` TODO가 남아 있었다.

### SSR만으로는 부족했던 이유

| devtools, 5회 중앙값             | `f693c2e` | `9a899a5` (SSR) | `adabb4a` (+애니메이션 생략) |
| -------------------------------- | --------- | --------------- | ---------------------------- |
| LCP 이미지 요청 시작             | 5,052 ms  | 641 ms          | 640 ms                       |
| LCP                              | 5,240 ms  | 5,117 ms        | 2,431 ms                     |
| 스크립트 실행 시간 (bootup-time) | 1,938 ms  | 2,616 ms        | 2,413 ms                     |

- SSR로 이미지 요청은 약 4.4초 앞당겨졌지만 LCP는 그대로였다.
- 게시글 목록은 framer-motion `initial="hidden"`으로 시작한다. 그래서 서버 HTML에서도 투명도 0이고, 하이드레이션이 끝나 애니메이션이 돌아야 보였다.
- 서버에서 받은 첫 페이지만 `initial={false}`로 바꾸자 LCP가 이미지 도착 시점 근처로 내려왔다.
- 스크립트 실행 시간은 SSR 이후 늘었다(하이드레이션 대상 증가). 다만 TBT는 범위가 겹쳐 차이 없음으로 판정했다.
- LCP 단계 분해(`lcp-breakdown-insight`)는 변경 전 측정에서 이미지 로드 단계가 비어 있어서 단계별 수치는 쓰지 않았다. 대신 요청 시작 시각만 `network-requests`에서 비교했다.

### 애니메이션을 생략하자 드러난 레이아웃 이동

- 날짜 바(`react-multi-carousel`)는 하이드레이션 전까지 날짜 항목을 그리지 않는다. 그래서 서버 HTML에서 높이가 0이고, 하이드레이션 후 70px가 된다.
- 피드가 투명할 때는 이 이동이 CLS로 집계되지 않았다. 피드가 처음부터 보이자 CLS 0.078로 측정됐다.
- 날짜 칸 높이(70px)만큼 최소 높이를 잡아 해결했다.

### 같은 시점에 확인했지만 이번에 다루지 않은 병목

1단계·2단계 진단에서 확인한 것들이다. 데이터셋은 게시글 1개였고, 커밋은 `f693c2e`다.

- **폰트:**
  - `globals.css`의 `@import` → jsdelivr CSS → `PretendardVariable.woff2` 2,010 KiB 체인이다.
  - 폰트를 차단한 실험(`channel-home--devtools-exp-block-font`, 3회)에서 FCP가 2,071 → 1,436 ms였다.
  - `/channels`의 총 전송량은 2,207 → 197 KiB였다.
- **아바타:** S3 원본(1,387 KiB)을 44px로 표시한다. 차단해도 LCP 변화는 없었다(`channel-home--exp-block-avatar`).
- **게시글 목록 API:** 댓글 수를 게시글마다 별도 쿼리로 조회한다(N+1). 서버 응답 시간에 미치는 영향은 측정하지 않았다.
- **S3 객체 Content-Type:** 업로드된 이미지 객체가 `multipart/form-data`로 저장된다. 이미지 최적화·캐시에 대한 영향은 미확인이다.

## 측정 방법

### 환경

| 항목        | 값                                                                                            |
| ----------- | --------------------------------------------------------------------------------------------- |
| 도구        | Lighthouse 13.6.0 (`pnpm dlx`, 의존성 추가 없음)                                              |
| 브라우저    | Chrome 156.0.8078.48 headless                                                                 |
| 머신        | Apple M5, Node v24.13.0                                                                       |
| 서버        | 로컬 프로덕션 빌드 `pnpm build && pnpm start -p 3000`                                         |
| 외부 서비스 | Supabase, S3는 실제 서비스 사용                                                               |
| 설정        | 모바일 기본 설정, `--only-categories=performance`                                             |
| 스로틀링    | devtools(주 지표)와 simulated(참고) 두 가지                                                   |
| 회차        | 세트마다 5회 측정하고 중앙값을 쓴다. 측정 전에 워밍업 1회(`warmup.json`)를 하며 집계에서 뺀다 |

### 로그인 상태 측정

- 채널 홈은 로그인이 필요하다.
- 전용 Chrome 프로필로 `pnpm dev`에서 로그인한 뒤, 그 프로필을 `--remote-debugging-port=9222`로 headless 실행한다. Lighthouse는 `--port=9222`로 그 Chrome에 붙는다.
- 쿠키 헤더(`--extra-headers`)는 서드파티 요청에도 붙어서 쓰지 않았다.
- 로컬 프로덕션 빌드의 OAuth 콜백은 운영 URL로 가기 때문에, 로그인은 dev 서버에서 한다.

### 데이터셋

- **구성:** 채널 `01e952eb-…` 2026-10-30, 게시글 11개, 모두 이미지 포함(첫 페이지 10개 + 2페이지 1개).
- **측정용 게시글:** 10개는 `perf/scripts/seed-posts.mjs`로 앱의 작성 화면을 통해 올렸다. 이미지는 macOS 기본 배경화면을 4032px JPEG로 변환해 썼고, 업로드 경로의 클라이언트 WebP 변환을 그대로 거쳤다.
- **동일성 확인:** `perf/scripts/dataset-snapshot.mjs`가 게시글 id, 이미지 여부, 댓글 수, 반응 수의 해시(지문)를 세트 앞뒤로 남긴다. 모든 세트가 `77b6651b58d5a625`였다.
- **"오늘" 조건:** 측정 시점에 2026-10-30은 "오늘"이었다(KST 04:30–05:16). 그래서 before/after 모두 실시간 구독이 켜진 같은 조건이다. 날짜가 지난 뒤 다시 측정하면 실시간 구독이 꺼져 수치가 다를 수 있다.

### 재현

```bash
# 1) 대상 커밋 빌드와 서버
git checkout <커밋>
pnpm build && pnpm start -p 3000

# 2) 로그인된 측정 전용 Chrome (절차는 perf/scripts/measure.sh 머리말)

# 3) 측정 세트: 데이터셋 지문 → simulated 5회 → devtools 5회 → 데이터셋 지문
perf/scripts/run-feed-set.sh feed11

# 4) 집계와 진단
node perf/scripts/summarize.mjs perf/results/<커밋>/mobile/feed11--devtools
node perf/scripts/diagnose.mjs perf/results/<커밋>/mobile/feed11--devtools/run-1.json
```

- 결과는 `perf/results/<커밋>[-dirty]/<폼팩터>/<라벨>/`에 저장된다.
- `src`, 설정, 의존성 파일에 커밋되지 않은 변경이 있으면 폴더 이름에 `-dirty`가 붙는다. 이 보고서의 모든 세트는 `dirty: false`다.

### simulated LCP를 근거에서 제외한 이유

simulated(Lantern) LCP 추정치는 같은 코드에서도 회차마다 크게 갈렸다. 반면 관측 LCP는 안정적이었다(`metrics` 감사의 `observedLargestContentfulPaint`).

| 커밋      | simulated LCP 5회 (ms)                     | 관측 LCP 5회 (ms)                     |
| --------- | ------------------------------------------ | ------------------------------------- |
| `f693c2e` | 21,766 · 21,842 · 13,224 · 21,119 · 13,899 | 1,385 · 1,472 · 1,062 · 1,212 · 1,049 |
| `adabb4a` | 3,472 · 3,470 · 3,474 · 3,471 · 3,401      | 867 · 2,737 · 626 · 633 · 823         |
| `cff48c8` | 1,532 · 3,456 · 13,684 · 13,759 · 13,757   | 321 · 509 · 792 · 743 · 617           |

- 2 MB 폰트 요청을 LCP 의존 관계에 넣느냐에 따라 추정이 갈리는 것으로 보이지만, 원인은 미확인이다.
- 그래서 개선 판정은 실제 네트워크·CPU 스로틀링을 거는 devtools 결과로만 한다.
- simulated 결과도 모두 `perf/results/<커밋>/mobile/feed11/`에 남겨 두었다. 참고로, simulated FCP는 SSR 이후 1,524 → 1,679 ms로 범위가 겹치지 않게 늘었다. devtools FCP는 차이가 없었다.

## 한계

- **실험실 수치다.** 로컬 머신과 로컬 프로덕션 서버에서 잰 값이다. 실제 사용자 환경(필드 데이터, Vercel 배포)의 수치는 측정하지 않았다.
- **조건이 좁다.**
  - 캐시 없는 첫 방문, 모바일 에뮬레이션, 게시글 11개 피드 하나만 측정했다.
  - 게시글이나 댓글이 더 많은 경우는 측정하지 않았다.
- **서버 쪽 비용이 있다.** SSR로 첫 페이지 조회가 서버로 옮겨 갔다. devtools TTFB는 차이가 없었지만(248 → 203 ms, 범위 겹침), Supabase 응답이 느린 경우는 측정하지 않았다.
- **중복 요청이 남아 있다.** 하이드레이션 후 SWR이 첫 페이지를 한 번 더 요청한다(백그라운드 재검증). LCP를 늦추지는 않지만 요청 1회가 남는다.
- **애니메이션이 바뀌었다.** 첫 진입 때 서버에서 받은 게시글은 등장 애니메이션 없이 표시된다.

  - 측정 계정의 닉네임과 사용자 id. 가릴 문자열은 레포 밖 파일로 `--terms`에 넘겨서 레포에 남기지 않았다.
